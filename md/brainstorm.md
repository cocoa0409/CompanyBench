# Brainstorm: Molly Agent 主观操作规范设计

## Part 1: Molly Digital 面临的复杂 Agent 任务全景分析

### 1.1 内部运营场景

#### 招聘全流程（跨系统、跨角色、多轮次）
- 用人部门主管提出HC需求 → 发布JD → 候选人投递 → 简历评估 → 多轮面试安排 → 面试反馈收集 → 录取/拒绝决策 → 谈薪 → offer发放 → 入职办理
- 复杂性：涉及 recruitment + schedule + email + employee + document 五个工具域；面试官按轮次由不同角色担任（R1主管/R2上级/R3 HRBP）；需跟踪评分并执行跳轮/录取/拒绝的条件判断；谈薪有上限约束（JD上限×120%）

#### 绩效管理季度循环
- 季度初设定OKR → 季度末提交review → 主管评定绩效 → 绩效结果影响年终奖计算
- 复杂性：需判断员工是否在季度首个工作日在职；主管评自己的绩效由上级完成；S级占比上限5%需要全局约束；年终奖公式涉及多变量计算

#### 假勤与薪资联动
- 员工请假 → 判断假期类型 → 优先扣减带薪假 → 审批链流转 → 影响年终奖计算（无薪天数）→ 年末未休假折算
- 复杂性：法定年假5天 + 司龄福利年假N天 + 带薪病假5天，不同假期有不同的扣减优先级；加班有3倍日薪计算；年末未休假以3倍日薪兑现

#### 资源审批链
- 员工申请设备 → 直属领导审批 → 财务主管审批 → 5个工作日内领取
- 复杂性：审批链的自动生成需要查询组织架构；逾期需重新申请；虚拟资产与实物资产处理不同

### 1.2 外部客户服务场景

#### 订单全生命周期管理
- 客户下单 → 支付（在线/银行转账）→ 打包发货 → 物流跟踪 → 签收确认 → 会员积分累计
- 复杂性：银行转账有手续费阶梯计算、3天付款截止期、每日11:00统一确认；在线支付实时到账；隔天达有14:00发货截止时间；妥投后7天自动确认

#### 退货退款流程
- 客户申请退货 → 判断退货类型（7天无理由/14天质量问题）→ 判断时间窗口 → 客户寄回 → 仓库验货 → 退款到原支付方式
- 复杂性：不同退货类型有不同的验收标准；不接受到付快递；手续费由客户承担；退款时限3个自然日；需区分正常磨损与质量问题

#### 会员体系管理
- 客户消费累计 → 过去6个月滑动窗口计算 → 等级判定（Platinum/Black Gold）→ 折扣与免运费权益
- 复杂性：只计入Completed订单的实付产品金额；折扣仅适用正价商品不适用特价和运费；等级可能升降

#### 客服工单处理
- 客户提交问题 → 分类（产品咨询/订单/技术支持/投诉）→ 分配处理人 → 解决 → 回复
- 复杂性：不同类型工单路由到不同部门；投诉需要升级处理；保修期外需转介制造商

### 1.3 跨域联动场景（最高复杂度）

- **新员工入职全链路**：offer谈妥 → 创建员工记录 → 分配部门权限 → 设备申请审批 → 安排入职培训 → 设定首季OKR → 邮件通知各方
- **员工离职处理**：标记离职 → 计算剩余年假折算 → 结算最后一个月薪资 → 回收设备 → 更新部门信息
- **大促运营**：批量调整特价标记 → 更新库存 → 发布促销文档 → 通知客服团队 → 处理突增工单和退货

## Part 2: 主观操作规范设计方案

### 2.1 设计原则

主观操作规范不是工具调用的时序编排，而是**业务语义层面的行为准则**。它定义的是 agent 在面对特定业务场景时"应该怎么做事"，而非"应该调用哪个API"。好的规范应该：

1. **隐含多步推理链**：规范表述简洁但执行时需要 agent 自行拆解为多个工具调用
2. **要求组织架构感知**：agent 必须理解汇报关系才能正确执行
3. **嵌入条件判断**：规范中包含"若...则..."的分支逻辑
4. **跨域协调**：单条规范可能横跨多个工具域
5. **存在隐式约束**：某些约束不直接体现在规范文字中，而需要 agent 从 policy 中推导

### 2.2 主观操作规范条目（按业务域分组）

#### A. 招聘与面试

| # | 规范 | 隐含的复杂度 |
|---|------|-------------|
| A1 | 创建面试记录时，必须同步在面试官和候选人的日历上创建对应日程事件，事件标题需包含候选人姓名、岗位及面试轮次 | 需查org确定面试官身份(R1主管/R2上级/R3 HRBP) → 创建interview → 为面试官create_event → 将事件与面试关联 |
| A2 | 每一轮面试安排完成后，必须邮件通知面试官并抄送所属部门HRBP，邮件中应包含候选人简历和面试日程信息 | 需查候选人简历 → 查部门HRBP → 发送邮件含正确CC |
| A3 | 面试反馈提交后，若已满足跳过第三轮的条件（前两轮均分 > 3.75），应主动通知HRBP当前状态并推进至谈薪环节，同时邮件通知候选人面试结果 | 需计算均分 → 条件判断 → 更新application状态 → 发送不同内容的邮件给不同角色 |
| A4 | 录用候选人时，需由HR主管发起谈薪，最终offer薪资不得超过JD上限的120%，谈薪结果须邮件抄送用人部门主管和CFO | 需查JD薪资范围 → 计算上限 → 验证offer合规 → 发邮件含正确CC列表 |
| A5 | 拒绝候选人时，必须以公司官方邮箱向候选人发送礼貌的拒绝通知邮件，并更新申请状态为Rejected | 需组织邮件内容 → 更新application状态 → 确保邮件发送方正确 |

#### B. 入职与员工管理

| # | 规范 | 隐含的复杂度 |
|---|------|-------------|
| B1 | 新员工入职当天，需完成：创建员工记录、发起设备申请（Laptop + Token）、安排首周入职培训日程、将入职指南文档以邮件发送给新员工 | 需连续调用employee/approval/schedule/document/email五个域 |
| B2 | 员工部门调动时，需同步更新员工记录的部门和汇报关系，并通知原部门和新部门的主管及HRBP | 需查两个部门的主管和HRBP → 更新employee → 批量发送通知邮件 |
| B3 | 员工离职标记后，需计算其剩余年假和带薪病假折算金额（3倍日薪标准），将计算结果邮件发送给薪酬专员和财务主管 | 需查leave_balance → 查salary获取月薪 → 计算日薪和折算金额 → 发邮件给Jennifer Wu和Thomas Moore |

#### C. 绩效与薪酬

| # | 规范 | 隐含的复杂度 |
|---|------|-------------|
| C1 | 季度首个工作日，为所有在职员工创建本季度OKR记录，并以邮件提醒每位员工与其直属上级协商制定OKR，截止日期为季度第二周周五 | 需查全量在职员工 → 批量创建OKR → 查每个员工的supervisor → 批量发送个性化邮件 |
| C2 | 部门主管提交绩效评定时，若同一部门内S级评定人数超过部门人数的5%，应拒绝并提醒主管调整 | 需查部门全量员工 → 统计已评S级人数 → 计算比例 → 条件拦截 |

#### D. 假勤与审批

| # | 规范 | 隐含的复杂度 |
|---|------|-------------|

#### E. 客户服务与订单

| # | 规范 | 隐含的复杂度 |
|---|------|-------------|
| E1 | 客户选择银行转账支付时，必须根据订单金额（产品+运费）查表计算手续费，将包含转账账户信息、应付总额（含手续费）、截止日期（下单日起3个自然日）的说明以邮件发送给客户 | 需查订单金额 → 阶梯计算手续费 → 计算截止日 → 组织邮件内容 |

| E5 | 客户确认收货（或自动确认）时，须将该笔订单的实付产品金额累加到客户会员消费记录中，并重新评估客户会员等级，若等级发生变化，需邮件通知客户新的会员权益 | 需confirm_receipt → 查客户近6个月消费 → 判断等级变化 → 条件性发送邮件 → update_customer |
| E6 | 处理客户产品咨询工单时，若涉及具体产品，应先查询产品信息（库存、价格、特价状态）后再回复；若客户为会员，需在回复中体现其会员折扣后的价格 | 需search_products → search_customers判断会员等级 → 计算折扣价 → submit_ticket_response |

### 2.3 构建 Benchmark 的挑战维度分析

上述规范对 agent 的能力构成以下维度的挑战：

| 维度 | 说明 | 示例规范 |
|------|------|---------|
| **组织架构推理** | Agent 必须根据目标员工的部门、层级动态推导出 supervisor / superior / HRBP 等角色 | A1, A2, A4, B2, C1 |
| **条件分支执行** | 规范中嵌入 if-else 逻辑，agent 必须先获取数据再做判断 | A3 (均分>3.75跳轮), D1 (年假余额判断), E3 (时间窗口校验), C2 (S级5%上限) |
| **数值计算** | 涉及薪资公式、手续费阶梯、折扣、日期差值等计算 | B3 (离职折算), C3 (年终奖公式), E1 (手续费阶梯), E4 (退款金额) |
| **跨域工具编排** | 单个任务需要横跨多个工具域协同完成 | B1 (5个域), A1 (3个域), E5 (3个域) |
| **批量操作** | 需要对集合中的每个元素执行操作，而非单一对象处理 | C1 (全量员工OKR), E2 (批量订单确认) |
| **隐式知识应用** | 规范本身不包含全部信息，agent需从policy中提取补充知识 | E1 (手续费表在policy中), A4 (120%上限在policy中) |
| **敏感信息管控** | Agent 必须理解信息的机密层级，控制邮件收件人范围 | F2 (薪资邮件权限), A4 (offer抄送范围) |
| **时间约束感知** | 需理解工作日、自然日、截止日期等时间概念 | E2 (每日11:00), E3 (7/14天窗口), D3 (5个工作日领取) |
| **业务状态机理解** | 理解订单、申请等实体的状态流转及合法转换 | E2 (Submitted→Paid/Canceled), A3 (Interviewing→Negotiating) |
| **自然语言生成** | 需根据上下文生成符合企业调性的邮件和回复内容 | F1, A5, E5 |

### 2.4 如何最大化 Benchmark 难度

1. **组合爆炸**：设计需要同时满足多条规范的任务（如"帮这位候选人安排第二轮面试"同时触发 A1+A2+可能的A3）
2. **规范冲突检测**：设计某些场景下两条规范可能产生张力，考验 agent 的优先级判断
3. **信息不完整**：用户指令故意模糊（如"处理一下张三的退货"），agent 需要主动查询补全信息才能执行规范
4. **边界条件**：设计恰好在阈值边缘的case（均分刚好3.75、退货刚好第7天、S级刚好5%）
5. **违规检测**：设计违反规范的操作请求，考验 agent 是否能识别并拒绝（如将offer薪资设为JD上限的150%）
6. **长链路追踪**：设计需要回溯历史操作结果才能做出当前决策的场景（如年终奖计算需回溯全年四个季度的绩效）
